# Conversational context, latency hiding and fast/slow design for a CPU-first small-model voice assistant (research notes, as of 2 Nov 2026)

Scope note: findings are sourced; anything specific to PAN (2B LFM3-Omni talker on a CPU-only mini PC, optional RTX 3050 box, Gemini free-tier fallback) is in the Inferences subsections. Older (pre-2025) sources are labelled "older". Vendor-reported numbers are labelled as such.

## 1. How do real-time voice stacks keep, trim and repair conversation history (Pipecat, LiveKit, OpenAI Realtime, Gemini Live), how much is kept, and what is recorded when the user interrupts?

### Takeaway
Every major stack keeps a growing message list with pinned system instructions and keeps far more history than "a few recent lines": Pipecat only starts summarizing at ~8,000 tokens or 20 messages (in the background, optionally with a cheaper model), OpenAI keeps up to 28,672 input tokens (gpt-realtime) or 128k (gpt-realtime-2) and drops oldest turns in big chunks to protect prefix caching, Gemini Live keeps a 128k window and slides it down to ~40% of the window when 80% full. On barge-in, the stacks store only the words the user actually heard.

### Cited Findings
**Pipecat**
- Built-in context summarization for the `LLMContext` aggregators is off by default; enable with `enable_auto_context_summarization=True` in `LLMAssistantAggregatorParams` — [Pipecat docs: context summarization](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization)
- Default triggers: `max_context_tokens` = 8,000 estimated tokens (about 4 characters per token) or `max_unsummarized_messages` = 20 new messages, whichever comes first; `min_messages_after_summary` keeps the most recent messages verbatim (docs cite 4 as the default) — [Pipecat docs: context summarization](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization)
- The rebuilt context is: system message (if it is the first message) + summary + recent messages. Mid-conversation system messages and "developer" messages are not protected and can be summarized away, so the docs say lasting instructions belong in `system_instruction` — [Pipecat docs: context summarization](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization)
- Summarization runs asynchronously in the background, can be routed to a separate cheaper LLM (`llm` in `LLMContextSummaryConfig`; those requests bypass the pipeline so the main conversation LLM is not interrupted), never splits incomplete function-call/result pairs, and can be triggered on demand with `LLMSummarizeContextFrame` (even exposed as a tool) — [Pipecat docs: context summarization](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization)
- The config names changed in v0.0.104 (`LLMContextSummarizationConfig` deprecated) — [Pipecat API reference](https://docs.pipecat.ai/api-reference/server/utilities/context-summarization)
- On interruption the TTS service drops pending text and word timestamps; the output transport releases text frames in step with playback, so unplayed text never reaches the assistant aggregator, which saves only the spoken-so-far text as the assistant message; an `interrupted` flag is exposed on `on_assistant_turn_stopped` — [Pipecat docs: interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions)
- Word-precise truncation depends on TTS word timestamps (Cartesia, ElevenLabs, Rime) — [Pipecat docs: text to speech](https://docs.pipecat.ai/pipecat/learn/text-to-speech)

**LiveKit Agents**
- `ChatContext.truncate()` keeps the most recent n items, always preserves system instructions even outside the window, and strips leading function-call items to avoid orphaned tool results; docs example `self.chat_ctx.copy().truncate(max_items=6)` when handing off to another agent; persistent edits go through `update_chat_ctx` (e.g. in `on_user_turn_completed`) — [LiveKit docs: chat context](https://docs.livekit.io/agents/logic/chat-context.md)
- LiveKit's multi-agent field guide warns truncation loses information for later agents and recommends keeping a canonical full history and deriving truncated contexts from it, optionally with a summary message — [LiveKit field guide](https://livekit.io/field-guides/guide/building-multi-agent-architectures)
- With synchronized transcription, text is emitted word by word with audio and truncated at the interruption point; word-level sync only works with the Cartesia, ElevenLabs and Rime plugins — [LiveKit docs: text and transcriptions](https://docs.livekit.io/agents/multimodality/text.md)
- A LiveKit community thread reports the chat context can still contain LLM text that TTS never voiced (e.g. interruption before speech started) and that the synchronizer's estimate "can be off by a word or two, especially for non-English languages"; workaround is to fix interrupted items on `conversation_item_added` (thread undated, may be outdated) — [LiveKit community](https://community.livekit.io/t/chat-context-contains-text-that-wasnt-spoken-due-to-interruption/165)
- Interruption defaults: `interruption.min_duration` 0.5 s; `resume_false_interruption` True (agent resumes if the "interruption" was not real speech) — [LiveKit docs: turn tuning](https://docs.livekit.io/agents/logic/turns/tuning.md)

**OpenAI Realtime**
- gpt-realtime: 32,768-token window, up to 4,096 output tokens, so max input 28,672; instructions + tools limited to 16,384 tokens; sessions up to 60 minutes (post undated; references the gpt-realtime-2025-08-28 snapshot) — [OpenAI developer notes on the Realtime API](https://developers.openai.com/blog/realtime-api)
- At 28,672 tokens the service auto-truncates oldest messages first; dropped messages are not summarized or compacted (developers must do that); `"truncation": "disabled"` makes oversize requests error instead — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)
- `retention_ratio` (example 0.8 drops 20% at once) deliberately truncates more than needed so truncation, and therefore cache busting, happens less often; trade-off is "lower cost but lower model memory for a given turn"; newer `token_limits.post_instructions` config exists — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api); [OpenAI realtime costs guide](https://developers.openai.com/api/docs/guides/realtime-costs)
- The GA service drops some audio tokens from context when a transcript is available — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)
- Prompt caching applies only to exact-match prefixes; truncation that alters the start of the conversation reduces the cacheable portion — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)
- gpt-realtime-2 (reasoning realtime model) has a 128k context window, up from 32k — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- For long sessions: "Do not rely on the model to infer source priority from a raw transcript or large context dump"; use labeled structure marking current vs stale sources — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- `conversation.item.truncate` exists because the server generates audio faster than real time; the client sends `audio_end_ms` (how much was actually played); "Truncating audio will delete the server-side text transcript" "to ensure there is not text in the context that hasn't been heard by the user"; server confirms with `conversation.item.truncated` — [OpenAI API reference: conversation.item.truncate](https://developers.openai.com/api/docs/api-reference/realtime-client-events/conversation/item/truncate)

**Gemini Live API**
- All Live API models have a 128k-token session context window; streamed audio accrues at 25 tokens per second (video 258 tokens/s) — [Firebase AI Logic: Live API sessions](https://firebase.google.com/docs/ai-logic/live-api/sessions)
- Without compression, audio-only sessions are limited to 15 minutes (audio+video 2 minutes); a single connection lasts about 10 minutes; `contextWindowCompression` with `slidingWindow` allows unlimited session length; session resumption tokens are valid 2 hours — [Google AI Studio docs: session management](https://aistudio.google.com/docs/live-api/session-management)
- Defaults: `triggerTokens` = 80% of the model's context limit (range 5,000 to 128,000); `targetTokens` defaults to 50% of the trigger; a very low target makes the model "rapidly forget" older turns — [Firebase AI Logic: Live API sessions](https://firebase.google.com/docs/ai-logic/live-api/sessions)
- The sliding window discards from the beginning, the retained context always begins at a USER turn, and system instructions are never discarded — [gemini_ex SDK docs mirroring the API reference](https://hexdocs.pm/gemini_ex/0.11.0/Gemini.Types.Live.SlidingWindow.md)
- Community report (unanswered): on gemini-3.1-flash-live-preview, changing `targetTokens` from 512 to 8,000 (trigger 25,000) changed post-compression audio session size by only ~10-20% — [Google AI developer forum](https://discuss.ai.google.dev/t/live-api-does-contextwindowcompression-target-tokens-affect-the-post-compression-window-for-audio-s2s-sessions/147228)

**Sesame**
- Sesame's CSM conditions speech generation on conversation history; trained on sequences up to 2,048 tokens (about two minutes of speech) to learn long-range conversational dependencies; "CSM sounds best when provided with context" — [Sesame research post](https://sesame.com/research)

### Inferences
- Convergent design across stacks: (a) pinned instructions are never trimmed; (b) a recent window stays verbatim; (c) older turns are either summarized off the critical path (Pipecat) or dropped rarely in large chunks to keep the cached prefix stable (OpenAI retention ratio, Gemini 80% to 40%); (d) the interrupted assistant turn is stored as heard-only text, flagged as interrupted.
- PAN's current "few recent lines" prompt is far more aggressive than any production default. Gemini's default keeps about 51k tokens after compression (50% of an 80% trigger on 128k), which at 25 tokens/s is roughly 34 minutes of audio; Pipecat does not even begin summarizing until 8,000 tokens. A text transcript of a voice session is much smaller than its audio-token equivalent, so a whole session can usually stay verbatim inside LFM3-Omni-2B's 32K window if prefill is cached (see section 2). Measure real session token counts from PAN logs to confirm.
- If PAN feeds raw audio into the omni model, store the text transcript (not audio tokens) in history, as OpenAI's GA service does, to keep context small.
- On barge-in, PAN should truncate the stored assistant message to what the phone actually played (playback position reported back to the hub), append a marker like "[interrupted]", and store the user's interjection as the next user turn. Without TTS word timestamps, estimate by playback time; LiveKit's experience says such estimates can be off by a word or two.
- Adopt LiveKit's "canonical full history plus derived prompt" pattern: the DB holds the full log; the prompt is rebuilt deterministically and append-only from it each turn, which is also what makes KV reuse possible.
- Summaries, if used, should be generated by the GPU box or cloud in the background (Pipecat's separate-LLM option), never by the 2B on the critical path.

### Gaps
- No official description found of how OpenAI's `auto` truncation picks boundaries (a community thread asking this had no official answer).
- No public documentation found on context policies inside consumer products (ChatGPT Advanced Voice, Gemini app Live).
- Did not verify whether the latest LiveKit SDK still leaves unspoken text in the chat context after early interruptions.

## 2. How can per-turn prompt cost be kept near zero on CPU (stable-prefix ordering, persistent KV cache, append-only context), and which architectures allow it?

### Takeaway
Prefix reuse only works if each turn's prompt starts with exactly the same tokens as the previous turn's. Full-attention models can reuse any matching prefix; sliding-window and recurrent/convolutional hybrids (LFM3 is one: 13 short-conv + 5 SWA-256 + 6 global attention layers) cannot roll back state and need saved state "checkpoints". Upstream llama.cpp's llama-server has supported context checkpoints for hybrid and recurrent models since October 2025, plus host-RAM prompt caching and slot save/restore; Liquid lists llama.cpp (GGUF, including a realtime speech server) as an LFM3-Omni engine and does not list Ollama.

### Cited Findings
- llama.cpp PR #16382 "implement context checkpointing for hybrid and recurrent models", merged 3 Oct 2025: extends SWA checkpointing to recurrent and hybrid models; "This removes the need to re-process the entire context in the majority of cases"; renames `--swa-checkpoints` to `--ctx-checkpoints`; checkpoints cover "the parts of memory that cannot be rolled back"; a logged checkpoint was 16.6 MiB for a ~4,000-token prompt (Jamba Mini); the server keeps the conversation up to the penultimate response and reprocesses the last one; early testers suspected a recurrent-state save/restore bug at the time — [llama.cpp PR #16382](https://github.com/ggml-org/llama.cpp/pull/16382)
- llama.cpp PR #16560 (merged 14 Oct 2025) added a dynamic token limit for the host-memory prompt cache (follow-up to #16391), bounded by `--cache-ram` — [llama.cpp PR #16560](https://github.com/ggml-org/llama.cpp/pull/16560)
- Mechanism (blog checked against llama.cpp master of 29 Jul 2026): full-attention KV can be truncated so needs no checkpoint; SWA KV and recurrent state cannot be rolled back, so checkpoints store only that non-reconstructible state; with no usable checkpoint the server logs "forcing full prompt re-processing due to lack of cache data" (trace level, needs `-lv 4`), resets to zero and erases checkpoints — [Particula Tech, 30 Jul 2026](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)
- Flags and defaults on master per that post: `--ctx-checkpoints` 32 per slot; `--checkpoint-min-step` 8192; `--cache-ram` 8192 MiB; `--cache-prompt` on; `--cache-reuse` 0; `--cache-idle-slots` on; `--swa-full` off; `-sps` (slot prompt similarity) 0.10; `--slot-save-path` disabled by default (enables manual /slots save and restore of full sequence state); `--log-prompts-dir` dumps prompts for diffing; `--checkpoint-every-n-tokens` was removed 25 May 2026 though guides still recommend it — [Particula Tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)
- Common prefix busters: stripped reasoning traces in earlier turns, tool definitions regenerated in a different order, harnesses that rewrite history in place; maintainer quote "You simply cannot cache something that changes." Mitigations: stop mutating the prefix, compact before hitting the slot limit, tune `-cms`/`-ctxcp`, use `--parallel 1` or raise `-sps` for single-user setups, or switch to full-attention models or vLLM/SGLang — [Particula Tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)
- Symptom of no reuse: TTFT of 0.62-0.87 s for a 701-token prompt versus 6.03-6.17 s for a 16,946-token prompt on every round — [Particula Tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)
- Other engines: vLLM's hybrid KV cache manager handles SWA plus full attention, with Mamba prefix caching experimental; SGLang has dedicated SWA and Mamba radix caches — [Particula Tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)
- LFM3-1.7B backbone (released 27 Oct 2026): 24 layers = 13 gated short convolutions (kernel 7, up from 3 in LFM2), 5 sliding-window attention layers with a 256-token window, 6 global attention layers; 256K context for the text model; a full 128K-token context needs 1.6 GB of KV cache versus 4.3 GB for Qwen3.5-4B and 5.6 GB for MiniCPM5-2B; about 1 GB at 4-bit; Liquid's on-device tests used llama.cpp at Q4_0 and 32K context (vendor) — [Liquid AI: Introducing LFM3](https://www.liquid.ai/blog/lfm3)
- LFM3-Omni-2B: 2.17B parameters, 32K context (input + output), non-reasoning ("enable_thinking=True is not supported"); BF16 runs on SGLang (text output only) and Transformers; GGUF runs on llama.cpp "including a realtime speech server"; each assistant turn opens with an empty `<think></think>` in the chat template — [Hugging Face model card](https://huggingface.co/liquidai/lfm3-omni-2b)
- The same exact-prefix principle governs cloud caching: only unchanged prefixes are cached and truncating the start reduces the cacheable portion — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)
- Practitioner note (not peer reviewed): a timestamp that changes every second makes every request a cache miss; a date-only string is recommended in the cached part — [tianpan.co](https://tianpan.co/blog/2026-04-20-temporal-context-injection-llm)

### Inferences
- With the owner's measured ~95 tok/s uncached CPU prefill, re-sending a 3,000-token history costs about 30 s per turn, while appending ~100 new tokens costs about 1 s. The fix for "forgets earlier conversation" is therefore runtime plus prompt layout, not a smaller window.
- LFM3's 1.6 GB per 128K tokens is roughly 12.5 KB per token, so a 5,000-token conversation's state is tens of MB. Keeping one warm slot per active conversation in RAM, and saving it to disk with `--slot-save-path` between sessions or across hub restarts, is cheap on a 29 GB machine.
- Recommended prompt layout (append-only): [static system prompt, persona, tool schemas, date only] then [append-only log: user turns, assistant turns as heard, tool results, thinker results, standing-instruction events] then an ephemeral tail [current time, retrieved memory hits, compact state block, new user utterance]. The tail is replaced each turn; since llama-server reprocesses the last turn anyway, replacing only the tail should cost roughly the tail's tokens. Retrieved memories placed before the history (as many RAG prompts do) change the prefix every turn and defeat caching.
- Keep the history rendering byte-identical across turns, including LFM3's empty `<think></think>` in past assistant turns; stripping or re-templating it reproduces the "stripped reasoning traces" cache-busting failure.
- Verify reuse on the real stack: run llama-server with `-lv 4` and check for "restored context checkpoint" and absence of "forcing full prompt re-processing"; diff prompts with `--log-prompts-dir`; use `--parallel 1` for a single user.
- Any compaction that rewrites the beginning (summaries) costs a full re-prefill. Do it rarely and in big chunks (the OpenAI retention-ratio logic), and precompute it in a second slot during idle time before switching.
- While the user is speaking, the partial transcript can be prefilled incrementally (same prefix, more tokens) so only the last few words remain at end of turn; whether checkpoint restore handles ASR revisions of the partial transcript on a hybrid model needs testing.
- If llama.cpp checkpointing misbehaves for LFM3, fallbacks are a full-attention small model (no checkpoint needed) or SGLang (SWA radix cache; but LFM3-Omni on SGLang is text-output only per the card).

### Gaps
- No source confirms llama.cpp checkpoint restore works correctly for LFM3's specific layer mix (kernel-7 short convs, 256-token SWA) or how the LFM3 realtime speech server manages caching. Must be tested.
- No CPU prefill/decode benchmarks for LFM3 or LFM3-Omni on Zen 3 class CPUs were found; Liquid gives only relative decode-speed claims.
- Did not check Ollama's current hybrid-model caching status directly; the owner's observation (no reuse) is consistent with the runtime lacking checkpoint support but is unverified here.

## 3. How do voice agents hide the latency of thinking, retrieval and tools, and what do users find natural vs annoying?

### Takeaway
Evidence says cut real latency first, then cover what remains: humans answer within ~200-250 ms, pauses near 1 s start to read as hesitation and longer pauses lower perceived competence, and above ~4 s quality of experience degrades. Natural, content-bearing fillers help most at long delays; artificial "processing" indicators did not help, and empty fillers can make an agent seem less intelligent. Products now generate short "preambles" before slow tools (OpenAI gpt-realtime-2 does it by default), run tools asynchronously while the conversation continues (OpenAI GA, Gemini NON_BLOCKING), and speculatively start generation before end of turn (LiveKit default, Deepgram EagerEndOfTurn).

### Cited Findings
**Human baselines and thresholds**
- Human turn gaps average 199 ms (Dutch) and 242 ms (English) (Hoogland et al. 2023); half of human response timings are under 350 ms (Sakuma et al., Interspeech 2023); a 2024 pause-perception study (replicated with Chinese listeners) found longer pauses make a responder seem less knowledgeable and less confident — [Deepgram blog, Sep 2026, citing the studies](https://deepgram.com/learn/voice-ai-latency-why-pauses-read-as-hesitation)
- Company claims: ~800 ms round trip is where callers notice lag; agents at or above 3 s scored in the mid-50s on Deepgram's quality index; conventional cascaded pipelines take 1,000-1,500 ms per turn (citing arXiv 2404.16053) — [Deepgram blog](https://deepgram.com/learn/voice-ai-latency-why-pauses-read-as-hesitation)
- CUI '25 study of LLM virtual agents in VR: latency above 4 s degrades quality of experience; natural conversational fillers (verbal and gestural) improve perceived response time, especially at high delay — [arXiv 2507.22352](https://arxiv.org/abs/2507.22352); artificial processing indicators had no significant effect — [UCF paper PDF](https://www.eecs.ucf.edu/isuelab/publications/pubs/maslychmCUI25.pdf); [Deepgram summary](https://deepgram.com/learn/voice-ai-latency-why-pauses-read-as-hesitation)
- A second 2025 VR study (embodied agents): any filler made response time more acceptable than none; contextualized fillers improved perceived competence (likeability unchanged); its literature review cites earlier work where agents using fillers were judged less intelligent; gestural fillers reduced perceived latency more than verbal ones (from search excerpt, not full-text verified) — [arXiv 2508.11781](https://arxiv.org/html/2508.11781v1)
- Vendor claim that fillers reduce perceived wait "by up to 40%" has no traceable study — [Dasha docs](https://blackbox.dasha.ai/docs/advanced-features/fillers.md)

**Starting work before the user finishes**
- LiveKit "preemptive generation" speculatively starts the LLM response before end of turn is confirmed and is enabled by default; if the chat context or tools change in `on_user_turn_completed`, the draft is discarded and regenerated; `max_retries` defaults to 3 — [LiveKit docs: turn tuning](https://docs.livekit.io/agents/logic/turns/tuning.md)
- Deepgram Flux: `EagerEndOfTurn` (moderate confidence the user stopped) starts a provisional LLM draft, `TurnResumed` cancels it; `eager_eot_threshold` 0.3-0.9, unset by default; if no TurnResumed occurs, the eager transcript equals the final one so the draft can be reused — [Deepgram eager EOT guide](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot); [Deepgram configuration](https://developers.deepgram.com/docs/flux/configuration.md)
- Cost/benefit: 50-70% more LLM calls — [Deepgram quickstart](https://developers.deepgram.com/docs/flux/quickstart.mdx); ~150 ms average saving reported by Telnyx — [Telnyx docs](https://developers.telnyx.com/docs/inference/ai-assistants/transcription-settings); 100-200 ms per Deepgram's blog — [Deepgram blog](https://deepgram.com/learn/voice-ai-latency-why-pauses-read-as-hesitation)
- SHANKS (Microsoft and NTU; ACL 2026): reasons over fixed-size chunks of user speech while the user is still talking; 37.1% higher interruption accuracy on a math step-checking task; completes 56.9% of tool calls before the user ends the turn; limitations are a one-chunk lag, redundant reasoning tokens and significantly higher compute — [arXiv 2510.06917](https://arxiv.org/abs/2510.06917)
- "Asynchronous Tool Usage for Real-Time Agents" (Salesforce, Oct 2024, older): event-driven finite-state machine that runs concurrent tools and responds as soon as any finishes, with an environment-managed notification role for tool start/finish, passage of time and interruptions; releases the first instruction-tuning dataset for async tool use — [arXiv 2410.21620](https://arxiv.org/abs/2410.21620)
- "Speculative Interaction Agents" (arXiv 2605.13360, 2026): asynchronous I/O plus speculative tool calling, reported 1.3-1.7x speedups with minor accuracy loss on strong cloud models (summary page) — [OpenTrain summary](https://www.opentrain.ai/papers/speculative-interaction-agents-building-real-time-agents-with-asynchronous-i-o-a--arxiv-2605.13360/)

**How products speak while thinking or calling tools**
- gpt-realtime-2 "generates preambles by default"; preambles and tool calls go in a "commentary" channel and the answer in "final"; `response.done` carries `phase` (`commentary` or `final_answer`) so apps can play commentary as a short update — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- OpenAI preamble rules: use before slow tool calls, multi-step reasoning, account/policy checks or escalation; skip for direct answers, confirmations, unclear audio, silence and lightweight tools; one short sentence; examples "I'll check that order now." and "I'll verify that before we make any changes."; avoid "Let me think about that for a second.", "Hmm..." and "I'm going to use my tools now."; preambles are not hidden chain-of-thought — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- gpt-realtime-1.5 example rule: "Before any tool call, say one short line like 'I'm checking that now.' Then call the tool immediately." — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- The realtime model follows sample phrases closely and may overuse them, so OpenAI recommends an explicit variety/repetition rule — [OpenAI realtime prompting cookbook](https://developers.openai.com/cookbook/examples/realtime_prompting_guide)
- OpenAI Realtime GA: async function calling keeps the session running while a call is pending; placeholder responses are inserted automatically, and if asked about a result that is not ready the model may say "I'm still waiting on that." — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)
- Gemini Live: function calls block by default; `behavior: NON_BLOCKING` lets the user keep talking while the function runs; the `FunctionResponse` sets `scheduling` to INTERRUPT (report now), WHEN_IDLE (after current speech) or SILENT (absorb and use later); async support is model-dependent (gemini-3.1-flash-live-preview does not support it; the docs list an extended-thinking Live variant that requires it) — [Google AI Studio docs: Live API tools](https://aistudio.google.com/docs/live-api/tools)
- OpenAI's Chat-Supervisor demo answers immediately and covers delegation with a filler such as "give me a moment to check on that"; about 2 s passes between the end of the filler and the substantive answer — [openai-realtime-agents README](https://github.com/openai/openai-realtime-agents)

### Inferences
- Order of operations for PAN: (1) remove real latency (KV reuse from section 2, incremental prefill during user speech, starting memory retrieval and tool calls on partial transcripts as SHANKS shows is feasible); (2) only when the expected wait exceeds roughly 1 s, speak a short, content-bearing acknowledgment that names the action ("Checking your calendar."); (3) never use empty thinking noises as the default.
- On a CPU shared by STT, the LLM and possibly TTS, speculative full generations (50-70% extra calls in cloud setups) are expensive; speculative prefill plus speculative retrieval gives most of the benefit at lower cost.
- Acknowledgments can be pre-synthesized and cached as audio so they play instantly; vary them from a small pool (OpenAI's variety rule), and suppress them when the real answer is ready first (Deepgram's tone guidance).
- Gemini's INTERRUPT / WHEN_IDLE / SILENT semantics are a good model for delivering late results from a slow thinker or tool: WHEN_IDLE for normal answers, INTERRUPT for corrections that matter, SILENT for background facts added to context for later.

### Gaps
- Filler/latency user studies are mostly VR or embodied agents; no controlled study found for audio-only phone or pendant assistants comparing content-bearing acknowledgments with generic fillers.
- No public technical detail found on how ChatGPT Advanced Voice or Sesame's consumer demo handle thinking pauses or tool calls.
- No measurements found of preemptive generation cost or benefit on CPU-only local models.

## 4. Fast/slow (talker/thinker) architectures: what exists, how is the handoff made seamless, and how do systems decide which turns need the big model?

### Takeaway
There is a clear 2024-2026 lineage: a fast talker keeps the conversation going while a slower, smarter model works in parallel and feeds it (Talker-Reasoner, OpenAI Chat-Supervisor, Sakana KAME, ConvFill, Mind-Paced Speaking, STITCH, SHANKS, Qwen-Omni Thinker-Talker). The no-training version (talker calls the thinker as a tool after a short preamble) costs ~2 s on hard turns; the trained version (talker absorbs streamed thinker hints mid-utterance) reaches near-zero added latency with most of the big model's quality (KAME: MT-Bench subset 2.05 to 6.43; ConvFill: within 6.3% of the frontier reasoner using 135M-1.7B talkers). Routing is mostly an explicit allow-list or self-escalation; learned routers (RouteLLM) are older but show large savings.

### Cited Findings
- Talker-Reasoner (Google DeepMind, Oct 2024, older): fast Talker handles conversation; slow Reasoner does multi-step planning, tool calls and belief/state updates; they communicate mainly through shared memory; the Talker can wait for the Reasoner when needed; deciding automatically when the Reasoner is needed is left as future work — [arXiv 2410.08328](https://arxiv.org/abs/2410.08328)
- OpenAI Chat-Supervisor: a realtime chat agent handles greetings, casual chat and information collection under an explicit "Allow List of Permitted Actions"; anything else goes through a `getNextResponseFromSupervisor` tool to a text supervisor (gpt-4.1, cheaper gpt-4.1-mini, or o4-mini) holding the domain prompt and tools; "the model responds to the user right away, even if it has to lean on the supervisor agent"; ~2 s from filler end to answer, versus stitched pipelines "often 1.5s or longer"; teams move one task at a time to the realtime model — [openai-realtime-agents README](https://github.com/openai/openai-realtime-agents)
- OpenAI's companion Sequential Handoff pattern: the model decides handoffs via tool calls and each handoff swaps instructions and tools with `session.update` — [openai-realtime-agents README](https://github.com/openai/openai-realtime-agents)
- KAME (Sakana AI, ICASSP 2026): Moshi-based speech-to-speech front end plus streaming STT plus back-end text LLM; the back end's evolving candidate answers are injected as a fourth "oracle" token stream; the front end consumes tokens about every 80 ms, back-end updates arrive every 100-500 ms, and the newest oracle wins — [KAME paper](https://arxiv.org/html/2510.02327v1); [Sakana blog](https://sakana.ai/kame-icassp-2026/)
- KAME results on an MT-Bench subset (reasoning, STEM, humanities): Moshi 2.05; KAME + GPT-4.1 6.43; KAME + Claude Opus 4.1 6.23 (both at Moshi-level latency); cascaded Unmute + GPT-4.1 7.70 at 2.1 s latency; the back-end alone 7.79; the back end can be swapped without retraining; limitations include redundant phrasing when revising after contradictory oracles and trailing cascaded quality because it "starts responding with significantly less information"; forced-delay experiments show quality improves with a little delay, with diminishing returns — [KAME paper](https://arxiv.org/html/2510.02327v1)
- KAME follow-up: "Learning Natural Conversational Behavior in Tandem Speech-to-Speech Models with Randomized Guidance" (details not retrieved) — [alphaXiv author page](https://www.alphaxiv.org/@yotaro-kubo)
- ConvFill, "Thinking While Speaking" (v1 Nov 2025, v3 Jul 2026): small talker responds immediately and integrates streamed knowledge from a large reasoner ("conversational infill"); seven talkers from 135M to 1.7B; 290,571 synthetic training examples over six domains; accuracy "within 6.3% of the corresponding frontier reasoner"; millisecond time-to-first-response; user study (n=18, talkers on an Apple M2): on par with frontier models overall, preferred for retrieval-heavy tasks, significantly more responsive — [arXiv 2511.07397](https://arxiv.org/abs/2511.07397)
- STITCH (Microsoft and NTU, ICLR 2026): alternates unspoken reasoning chunks with spoken chunks, using each audio chunk's playback time to generate the next reasoning chunk; same latency as no-reasoning baselines, +15% on math reasoning, equal on non-reasoning tasks — [arXiv 2507.15375](https://arxiv.org/abs/2507.15375)
- Mind-Paced Speaking (StepFun with NTU, Oct 2025): "dual-brain" design, one part reasons continuously while the other speaks; 92.8% on Spoken-MQA and 82.5 on URO-Bench in a zero-latency setting, comparable to think-then-speak models; underlies Step-Audio R1.1 Realtime — [arXiv 2510.09592](https://arxiv.org/abs/2510.09592); a 2026 paper classifies it as half-duplex (does not listen while reasoning) — [arXiv 2606.07547](https://arxiv.org/abs/2606.07547)
- Listen-Write-Speak (May 2026): one LLM listens, writes visible text as its main output and speaks in parallel from a shared context; 4.72 on VoiceBench AlpacaEval and 92.6% writing-speaking consistency — [arXiv 2606.07547](https://arxiv.org/abs/2606.07547)
- Qwen3-Omni (Sep 2025): Thinker (text) and Talker (speech) are both MoE; the Talker no longer consumes the Thinker's text representations and can have its own system prompt; multi-codebook generation with a multi-token-prediction module and causal ConvNet decoder; theoretical cold-start first-packet latency 234 ms — [arXiv 2509.17765](https://arxiv.org/abs/2509.17765)
- Moshi (Kyutai, Sep 2024, older): "Inner Monologue" predicts time-aligned text tokens as a prefix to audio tokens; theoretical latency 160 ms, about 200 ms in practice — [arXiv 2410.00037](https://arxiv.org/abs/2410.00037)
- RouteLLM (LMSYS, Jul 2024, older): routers trained on Chatbot Arena preference data; on MT-Bench a matrix-factorization router reached 95% of GPT-4 quality with 26% GPT-4 calls (about 48% cheaper than random routing), and 14% GPT-4 calls (about 75% cheaper) with LLM-judge-augmented training data; routers transferred to a Claude 3 Opus / Llama 3 8B pair without retraining — [LMSYS blog](https://lmsys.org/blog/2024-07-01-routellm/)
- Prompt-level routing in OpenAI's reasoning voice model: "For direct answers, simple lookups, and short confirmations, respond quickly and do not reason"; "For multi-step tasks, tool decisions, troubleshooting, or escalation, reason before acting"; start with `reasoning.effort: "low"` — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)

### Inferences
- Tier A for PAN (no training, ships first): Chat-Supervisor pattern. The 2B talker answers allow-listed turns (greetings, acknowledgments, confirmations, short chit-chat, reading back results) and otherwise calls an `ask_thinker` tool after a one-line preamble; the thinker (RTX 3050 box locally, Gemini as fallback) always receives the full canonical history plus memory and returns final wording; the talker speaks it in the same voice.
- Seamless handoff means one voice, one log: TTS stays the same, the thinker's answer is written into the shared history as the assistant's own turn (so later turns "remember" it), and the talker never contradicts a pending thinker answer (Talker-Reasoner's shared-memory idea).
- Tier B (trained): KAME/ConvFill-style hint channel where the talker starts speaking and blends in thinker content as it streams. This needs training data with simulated thinker hints at varying completeness, which the 31B teacher can generate (see section 6).
- Routing v1: escalate on (i) any fact lookup or tool need, (ii) references to things outside the talker's context, (iii) multi-step or reasoning intents, (iv) talker self-escalation (an `escalate` tool it is trained to call when unsure), (v) standing instructions the 2B cannot execute well (for example sustained Japanese translation). Later, train a RouteLLM-style router on logged turns where the teacher labels whether the 2B's answer was acceptable.
- STITCH/MPS-style interleaved reasoning inside the 2B itself is unlikely to help much on CPU because the model is already at its reasoning ceiling; quality gains should come from the bigger thinker.

### Gaps
- No published system found that pairs a CPU-only ~2B talker with a local GPU 4-9B thinker and reports end-to-end latency and quality; ConvFill on an M2 is the closest.
- No user-perception data found on audible style changes when a thinker's answer is read by the talker.
- RouteLLM-style routing evidence is from 2024 text chat, not voice.

## 5. What does the evidence say about small-model competence in multi-turn conversation, and which 1-4B models are strongest in 2026?

### Takeaway
Multi-turn conversation is hard for all models: performance drops ~35-39% from single-turn to underspecified multi-turn even for frontier models, mostly from unreliability rather than lost capability, and lowering temperature does not fix it. The capabilities that improve with scale (instruction retention, remembering user-provided info) are exactly PAN's complaints, and small models are measurably weaker at multi-turn function calling. No independent 2026 multi-turn leaderboard covers 1-4B models; vendor tables put LFM3-1.7B ahead on instruction-following benchmarks (IFEval, Multi-IF) but behind Qwen3.5-4B on knowledge/reasoning and behind Gemma 4 E4B on VoiceBench.

### Cited Findings
- "LLMs Get Lost In Multi-Turn Conversation" (May 2025; ICLR 2026 per coverage): 15 models, six tasks; average 39% drop from fully specified single-turn to "sharded" multi-turn; aptitude falls ~16% while unreliability rises ~112%; failure modes are premature answer attempts, bloated later answers and ignoring middle turns; degradation appears even in two-turn conversations — [arXiv 2505.06120](https://arxiv.org/html/2505.06120v1); [beam.ai on ICLR 2026](https://beam.ai/agentic-insights/iclr-2026-llms-lose-accuracy-in-multi-turn-conversations)
- Same paper, sharded performance as a share of full: Llama3.1-8B ~62.5%, Phi-4 ~61.7%, GPT-4o-mini ~56.2%, GPT-4o ~57.9%, Gemini 2.5 Pro ~64.5%; smaller models degrade more in the "Concat" setting; lower temperature cuts unreliability 50-80% in single-turn but barely helps multi-turn; mitigations for GPT-4o-mini/GPT-4o: Sharded 50.4/59.1, Snowball (restate all prior user info each turn) 61.8/65.3, Recap 66.5/76.6, Full 86.8/93.0 — [arXiv 2505.06120](https://arxiv.org/html/2505.06120v1)
- MultiChallenge (Scale, Jan 2025): four categories (instruction retention, inference memory of user info, reliable versioned editing, self-coherence including resisting sycophancy); all frontier models under 50%, top 41.4% — [arXiv 2501.17399](https://arxiv.org/abs/2501.17399)
- MultiChallenge update (Mar 2026): 54 tasks revised; Gemini 3 Pro 65.67 overall; inference memory and instruction retention improve most with scale while self-coherence and versioned editing stay hard; open-weight models trail, most on versioned editing and inference memory — [Scale Labs blog](https://labs.scale.com/blog/multichallenge-update); live leaderboard top 75.52 at time of search — [Scale leaderboard](https://scale.com/leaderboard/multichallenge)
- Multi-IF (Meta, Oct 2024, older): IFEval extended to 3 turns, 4,501 conversations, 8 languages; o1-preview falls from 0.877 at turn 1 to 0.707 at turn 3; non-Latin scripts (Hindi, Russian, Chinese) show higher error — [arXiv 2410.15553](https://arxiv.org/abs/2410.15553)
- EvolIF (Nov 2025): longer evolving dialogues; GPT-5 sustains 14 turns with 66.40% robustness — [arXiv 2511.03508](https://arxiv.org/abs/2511.03508)
- Instruction/persona drift (Li et al., COLM 2024, older): significant drift within eight rounds for LLaMA2-chat-70B and GPT-3.5, attributed to attention decay toward the system prompt; split-softmax at inference trades performance for stability better than prompting baselines — [arXiv 2402.10962](https://arxiv.org/abs/2402.10962)
- TinyLLM (Nov 2025): with prompt-based function calling, Qwen3-4B and Qwen3-1.7B scored 16.88% and 8.38% in multi-turn; the authors conclude multi-turn dialogue is especially sensitive to model size — [arXiv 2511.22138](https://arxiv.org/abs/2511.22138)
- Small models on context-summarized multi-turn customer-service QA (Jan 2026, Frontiers in AI): nine SLMs vs three LLMs; some near-LLM, others struggle with dialogue continuity (abstract only) — [arXiv 2602.00665](https://arxiv.org/abs/2602.00665)
- Liquid's table (vendor, Oct 2026): LFM3-1.7B IFEval 96.66, IFBench 73.03, Multi-IF 89.10, BFCL v4 71.39; Qwen3.5-4B IFEval 92.52; Gemma 4 E4B IFEval 90.02 / Multi-IF 81.03; Qwen3.5-9B Multi-IF 84.44; but GPQA Diamond LFM3 63.37 vs Qwen3.5-4B 75.76 and Qwen3.5-9B 80.40; Liquid states "Larger models still win on agentic coding and knowledge, where size matters most" — [Liquid AI: Introducing LFM3](https://www.liquid.ai/blog/lfm3)
- LFM3-Omni-2B (vendor): VoiceBench 64.73 vs Qwen2.5-Omni-3B 66.37 and Gemma 4 E4B 72.90 in Liquid's own comparison; internal tool-calling eval 52.20; greedy decoding recommended for text output — [Hugging Face model card](https://huggingface.co/liquidai/lfm3-omni-2b)
- End-to-end speech model without a thinker: Moshi scores 2.05 on KAME's MT-Bench subset — [KAME paper](https://arxiv.org/html/2510.02327v1)
- With a thinker feeding it, a 135M-1.7B talker gets within 6.3% of the frontier reasoner — [arXiv 2511.07397](https://arxiv.org/abs/2511.07397)
- Third-party listicles name SmolLM3-3B, Qwen3-4B, Gemma 3 4B and Phi-4-mini as strong small models but give no multi-turn chat scores (low-quality evidence) — [PremAI](https://blog.premai.io/best-lightweight-language-models-worth-running)

### Inferences
- The evidence does not establish a minimum size for coherent multi-turn conversation; even frontier models get lost. But the failure categories that shrink with scale are the ones PAN shows, so a 2B will need external help: full context, a state block, and a thinker.
- IFEval and Multi-IF test verifiable format constraints over at most three turns. LFM3's high scores suggest that when a standing instruction is actually in the prompt, the model can follow it. PAN's "ignores standing instructions" is therefore probably mostly a context-construction problem (the instruction has scrolled out of the short prompt), which is testable.
- Facts and times are a knowledge/reasoning problem where 2B models are weakest (GPQA gap, Liquid's own caveat); route those to tools or the thinker rather than training the 2B harder.
- For the GPU thinker, Qwen3.5-4B/9B and Gemma 4 E4B are the natural candidates from vendor tables; choose by an in-house eval rather than by vendor numbers.
- Build a PAN multi-turn eval on MultiChallenge's four axes plus PAN-specific cases (a "from now on, translate into Japanese" instruction tested 10+ turns later, references to early turns, time/date questions, corrections). Run each case with (a) the current short prompt, (b) full history, (c) full history plus state block, to separate context failures from model ceiling.

### Gaps
- No independent multi-turn scores (MultiChallenge, MT-Bench-101, EvolIF) found for 2026 1-4B models (Qwen3.5-2B/4B, Gemma 4 E2B/E4B, LFM3); only vendor tables. Qwen3.5 small-model card numbers could not be confirmed.
- No spoken (audio-in) multi-turn benchmark results found for small models; VoiceBench is mostly single-turn.
- MT-Bench-101 was not retrieved in this pass.

## 6. How should a small model be trained for spoken dialogue behaviour (datasets, multi-turn distillation, brevity, follow-ups, persistent instructions, corrections), and what are the pitfalls?

### Takeaway
Train on whole sessions, not single turns, and let the student learn from its own mistakes: on-policy distillation (student generates, teacher scores every token) is 9-30x cheaper than extended SFT for reaching the same quality, fixes exposure bias, and restored instruction-following after a personal-knowledge fine-tune crushed it (IF-eval 85% to 45%, back to 83%). Multi-turn variants (prefix replay) make this affordable. Data should deliberately contain context-dependent follow-ups, standing instructions, corrections and abstentions, at spoken length; synthetic spoken data works best mixed with some real data.

### Cited Findings
- On-policy distillation (Thinking Machines, 27 Oct 2025): student samples its own trajectories and the teacher scores every token (per-token reverse KL); reached 70% on AIME'24 in ~150 steps; 9x cheaper than extended SFT if the SFT data exists, 30x including teacher sampling; off-policy SFT pitfalls are compounding errors, exposure bias, imitating the teacher's style and confidence without its accuracy, and forgetting — [Thinking Machines blog](https://thinkingmachines.ai/blog/on-policy-distillation/)
- Same post, personalization case (Qwen3-8B): IF-eval 85% at baseline; 45% after mid-training on 100% internal documents; 79% with a 70% documents / 30% chat mix; 83% after adding on-policy distillation, while internal-knowledge QA went from 18% to 41% — [Thinking Machines blog](https://thinkingmachines.ai/blog/on-policy-distillation/)
- Multi-turn on-policy distillation with prefix replay (ReOPD, Jul 2026): replaces live rollouts with pre-collected teacher trajectories, the student acts at the supervised step and the teacher supplies per-step targets; at least 4x faster per training step while preserving or improving accuracy; identifies a "prefix trap" (more student-like histories can push the teacher into states where its guidance is unreliable) and uses a step-decaying schedule that favours early prefixes — [arXiv 2607.04763](https://arxiv.org/abs/2607.04763); summaries mention Qwen3-4B student / Qwen3-30B-A3B teacher experiments, but attribution between this paper and a related one is unclear — [arXiv 2609.14636](https://arxiv.org/pdf/2609.14636)
- Parrot (ACL 2024, older): most instruction data neglects multi-turn dependencies; a user simulator trained on real conversations generates context-dependent follow-ups (anaphora, ellipsis); CaPO preference training uses negatives that ignore context or misread anaphora; up to 7.2% gain in multi-turn instruction following; extends MT-Bench to 8 turns (MT-Bench++) — [arXiv 2310.07301](https://arxiv.org/abs/2310.07301)
- KAME's training recipe for a talker that consumes thinker hints: simulated oracle hints at levels 0-5 keyed to the fraction of user words heard (no hint below 50%, ground truth at 100%); sessions built from MMLU-Pro (22,800), GSM8K (11,742) and HSSBench (22,040) converted to speech with TTS; timing jitter added; audio loss weighted 1.5 — [KAME paper](https://arxiv.org/html/2510.02327v1)
- ConvFill trained its talkers on 290,571 synthetic examples across six domains — [arXiv 2511.07397](https://arxiv.org/abs/2511.07397)
- DeepDialogue (May 2025): 40,150 multi-turn dialogues, 41 domains, 20 emotions, voiced by TTS (XTTS conditioned on emotional reference audio) — [arXiv 2505.19978](https://arxiv.org/abs/2505.19978)
- OmniChat / ShareChatX (Jan 2025): LLM-written scripts voiced by controllable TTS with ASR word-error filtering; found an optimal balance of synthetic and real data and reached state of the art on the real DailyTalk dataset — [arXiv 2501.01384](https://arxiv.org/abs/2501.01384)
- InteractSpeech (EMNLP 2025 Findings): 150-hour corpus for interruptions and backchannels, partly synthetic, partly filtered real dialogue — [papers.cool listing](https://papers.cool/venue/2025.findings-emnlp.424@ACL)
- Async tool-use instruction data exists from the Salesforce real-time agents paper (older) — [arXiv 2410.21620](https://arxiv.org/abs/2410.21620)
- Target lengths from OpenAI's voice guidance: direct answers 1-2 short sentences; one clarifying question at a time; troubleshooting one step at a time; older global cap of 2-3 sentences per turn — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- Failure modes to train against: premature answers when information is incomplete, answer bloat, ignoring middle turns — [arXiv 2505.06120](https://arxiv.org/html/2505.06120v1); sycophantic reversals under user pushback — [arXiv 2501.17399](https://arxiv.org/abs/2501.17399)
- LFM3 is designed to be fine-tuned on a single GPU (vendor) — [Liquid AI: Introducing LFM3](https://www.liquid.ai/blog/lfm3)

### Inferences
- If the 2B student was trained on teacher labels for short single-turn prompts, it was taught to ignore context. Rebuild training data as full sessions (roughly 10-40 turns) rendered exactly in the deployed prompt layout (static head, append-only history, ephemeral tail with state block and time), with loss on every assistant turn.
- Seed sessions with the phenomena PAN fails on: a standing instruction set early and tested many turns later; "no wait, I meant..." corrections that must update state; anaphora and ellipsis; versioned edits; questions whose answer is not in context, where the right move is "I don't know, want me to check?" or an escalate/tool call; underspecified requests where the right move is one short follow-up question.
- Use the 31B teacher twice: as a user simulator plus writer of full sessions, and as the on-policy distillation teacher scoring the 2B's own multi-turn rollouts (prefix replay keeps cost down).
- Rewrite teacher outputs to spoken length before training; verbosity from a text teacher is a classic voice failure.
- If PAN fine-tunes on the owner's personal data, keep a substantial general-chat share (the 30% chat mix kept IF-eval at 79% vs 45%) and finish with on-policy distillation.
- If adopting tier B fast/slow, add KAME-style simulated thinker hints to the sessions so the talker learns to use them.
- Mix synthetic TTS audio with real recordings (OmniChat's finding); for a cascaded pipeline the text side matters more, but ASR noise (misrecognitions) should appear in training transcripts.

### Gaps
- Primary sources for CANDOR, Switchboard, Fisher and DailyTalk (sizes, licences, suitability) were not retrieved in this pass; DailyTalk appears only as OmniChat's evaluation set.
- No paper found that distills a ~2B voice assistant from a ~30B teacher over full sessions and reports multi-turn gains; how many sessions are needed to fix standing-instruction retention at 2B is unknown.

## 7. How should conversational state beyond raw text (topic, open questions, corrections, standing instructions, persona) be tracked so a small model can follow it?

### Takeaway
Production guidance converges on putting durable rules in a protected instruction slot that summarization and truncation never touch, using short labeled sections rather than raw transcript dumps, and making the current state explicit. Research backs re-stating key state near the end of the prompt: restating prior user information each turn ("Snowball") recovers part of the multi-turn loss, and instruction drift is explained by attention decay toward a distant system prompt.

### Cited Findings
- OpenAI's recommended voice prompt sections: role, tone, language, reasoning, preambles, verbosity, tools, unclear audio, entity capture, long-context behavior, escalation; older model example uses a state machine (Greeting, Discover, Verify, Diagnose, Resolve, Confirm/Close) with an "Exit when" condition per phase, with `session.update` swapping instructions and tools per phase; collect required values one at a time and confirm identifiers before tool calls — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- For long sessions, use labeled structure to mark current versus stale sources rather than relying on the model to infer priority from a raw transcript — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- Clearly labeled sections help the model "stay consistent across turns"; capitalize key rules; convert conditional logic to plain-text rules; pin the output language — [OpenAI realtime prompting cookbook](https://developers.openai.com/cookbook/examples/realtime_prompting_guide)
- Language persistence rule example: English by default, switch only if the user explicitly asks or says something substantive in another language; accent alone must not change the language — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- Durable instructions must live in protected slots: Pipecat's `system_instruction` survives summarization while developer messages do not — [Pipecat docs](https://docs.pipecat.ai/pipecat/fundamentals/context-summarization); Gemini's sliding window never discards system instructions — [gemini_ex SDK docs](https://hexdocs.pm/gemini_ex/0.11.0/Gemini.Types.Live.SlidingWindow.md); LiveKit's `truncate()` always keeps system instructions — [LiveKit docs](https://docs.livekit.io/agents/logic/chat-context.md)
- Talker-Reasoner keeps a shared memory of beliefs that the slow Reasoner updates and the fast Talker reads — [arXiv 2410.08328](https://arxiv.org/abs/2410.08328)
- Restating prior user information each turn (Snowball) recovered roughly 15-20% of the multi-turn loss; a single recap turn recovered more but presumes knowing when the conversation ends — [arXiv 2505.06120](https://arxiv.org/html/2505.06120v1)
- Instruction drift within eight rounds is attributed to attention decay toward the system prompt; split-softmax boosts attention to it at inference — [arXiv 2402.10962](https://arxiv.org/abs/2402.10962)
- What must persist, per MultiChallenge: instructions from early turns, information the user provided, the latest version of edited content, and the model's own earlier claims (without caving to contradictory pushback) — [arXiv 2501.17399](https://arxiv.org/abs/2501.17399)

### Inferences
- Proposed compact state block for PAN (target under ~150 tokens), placed in the ephemeral tail every turn: ACTIVE INSTRUCTIONS (each with the turn it was set), LANGUAGE AND STYLE, CURRENT TOPIC, OPEN QUESTIONS / PENDING TASKS, CORRECTIONS (latest wins), FACTS ESTABLISHED THIS SESSION, one persona line. Recency counters attention decay, while the history itself stays append-only for the KV cache.
- The block should be maintained off the critical path by the thinker or a background extraction pass after each turn, not by the 2B while it is answering.
- Standing instructions ("from now on...") should be detected (cheap pattern check plus thinker confirmation), written to state, logged as an event in the history, and acknowledged briefly. Corrections should be stored as versioned entries with latest-wins semantics.
- If a standing instruction exceeds the 2B's ability (for example ongoing Japanese translation), the router should send those turns to the thinker while the state block keeps the instruction alive.

### Gaps
- No benchmark found that measures small-model gains from a structured state block versus raw history; this needs an in-house A/B test.
- Structured-flow frameworks (for example Pipecat Flows) were not reviewed in this pass.

## 8. How do voice assistants stop made-up facts and times without slowing down (time injection, tool calls, retrieval, refusing or asking)?

### Takeaway
Hallucination is partly a training incentive problem (guessing is rewarded over saying "I don't know"), and small models are worst at stored knowledge but can be trained to know their limits more cheaply than to be accurate. The working pattern is: inject the clock, answer facts only from tools/retrieval or a bigger model, start those lookups early, speak a short preamble while they run, and train the small model to abstain or ask when the answer is not in its context.

### Cited Findings
- OpenAI (Sep 2025): accuracy-only evaluation rewards guessing because "I don't know" scores zero; proposes penalizing confident errors more than abstentions and giving partial credit for uncertainty; argues a small model can more easily know its limits and that calibration needs much less computation than accuracy (illustrative example, not a benchmark) — [OpenAI: Why language models hallucinate](https://openai.com/index/why-language-models-hallucinate/)
- Liquid: "Larger models still win on agentic coding and knowledge, where size matters most" — [Liquid AI: Introducing LFM3](https://www.liquid.ai/blog/lfm3)
- Gemini Live docs claim grounding with Google Search "increases the Live API's accuracy and prevents hallucinations" (vendor claim); search can be combined with function declarations — [Google AI Studio docs: Live API tools](https://aistudio.google.com/docs/live-api/tools)
- OpenAI voice rules relevant to grounding: "Only report success after the tool call succeeds"; confirm exact identifiers before tool calls; "Do not reason when the audio is unclear"; ask "Sorry, could you repeat that clearly?" and do not repeat the same clarification twice; a `wait_for_user` tool for speech not addressed to the assistant — [OpenAI voice prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
- Injecting a stronger model's knowledge into a fast speech model lifted KAME's MT-Bench subset score from 2.05 to 6.43 with no added latency — [KAME paper](https://arxiv.org/html/2510.02327v1); users preferred ConvFill's talker-plus-reasoner for retrieval-heavy tasks — [arXiv 2511.07397](https://arxiv.org/abs/2511.07397)
- Starting tools during user speech: SHANKS completed 56.9% of tool calls before the user finished — [arXiv 2510.06917](https://arxiv.org/abs/2510.06917)
- Temporal benchmarks: EvolveBench (ACL 2025) tests temporal awareness including spotting misalignment between inputs and the query's time frame — [ACL Anthology 2025.acl-long.788](https://aclanthology.org/2025.acl-long.788); DateLogicQA (190 questions) catalogs temporal hallucinations from date tokenization and context failures — [arXiv 2412.13377](https://arxiv.org/abs/2412.13377)
- Practitioner reports (not peer reviewed): models answer with their training-cutoff year despite a date in the system prompt; telling the model that the injected date takes precedence helps; per-second timestamps break prompt caching — [tianpan.co](https://tianpan.co/blog/2026-04-20-temporal-context-injection-llm)
- Pending async results: OpenAI's GA Realtime model may say "I'm still waiting on that" instead of inventing a result — [OpenAI developer notes](https://developers.openai.com/blog/realtime-api)

### Inferences
- Time: put the date in the cached head (changes once a day) and the exact local time in the ephemeral tail each turn, with an explicit "this is the current time" label; answer pure clock questions ("what time is it", "what day is Thursday") deterministically from the system clock or a template, since these are the most frequent and most checkable fabrications.
- Personal facts: only from memory retrieval; when retrieval returns nothing, pass an explicit "no memory found" marker and train the model to say it does not know or offer to look it up.
- World facts and anything numeric: route to a tool or the thinker; start the lookup on the partial transcript; cover remaining delay with a one-line preamble; deliver with WHEN_IDLE-style timing.
